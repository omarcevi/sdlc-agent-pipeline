# Agent Spec

The full design is in `docs/superpowers/specs/2026-09-29-sdlc-agent-pipeline-design.md`. If this summary and that document conflict, the full design wins.

## Overview
An ADK 2.x graph `Workflow` that turns a GitHub issue into a tested PR. The steps are:

1. Fetch the issue.
2. Provision a hermetic sandbox.
3. Planner (LLM) decides whether the issue is actionable and plans the work.
4. Coder (LLM) edits code, then its diff is collected and the tests are run (function nodes).
5. Reviewer (LLM) approves or requests changes.
6. A human approves.
7. Open the PR.

Loops are bounded: at most 3 test-fix attempts and 2 review rounds. A single-agent baseline uses the same tools, and both are measured by a hidden-test benchmark.

## Language
`python`

## Example Use Cases
- Input: an issue labelled `agent-ok` on a demo repo, e.g. "`--due` flag crashes on ISO dates with timezone". Output: a PR with a fix and a regression test, and all tests passing.
- Input: an ambiguous or impossible issue. Output: no PR; a comment explaining why it was declined.
- Input (bench mode): a task from `bench/tasks/<id>`. Output: a patch file plus a results record (resolved, cost, time, attempts).

## Tools Required
- `read_file`, `list_dir`, `grep`: read-only, used by Planner, Coder and Reviewer.
- `edit_file` (exact string replace) and `write_file` (new files only): Coder.
- `bash`: Coder. Runs in the sandbox with a 120 s timeout and 10k-character output cap.
- GitHub API (issues, branches, PRs, comments): orchestrator nodes only. Uses a fine-grained PAT from Secret Manager (`.env` locally). The PAT is never visible to models or the sandbox.

## Constraints & Safety Rules
- The sandbox has no network and no credentials. It runs as non-root with CPU, memory and process limits.
- Writes are allowed only inside the repo. Test files that existed at the base ref are read-only, and so is `.github/`.
- Refused commands: `git push`, `git remote`, `curl`, `wget`, `pip install`, `uv add`, and `rm` outside the repo.
- Live mode processes only issues labelled `agent-ok`. Issue text is treated as untrusted data. A human approves before any PR opens.
- Per-run caps: $1.00 and 75 tool calls. Multi-agent coder turns also have a 25-tool-call sub-limit.

## Success Criteria
- Benchmark: resolve rate on the dev (15) and held-out (5) splits, $/issue and median time, for multi- vs single-agent, at least 2 model presets, 3 repeats.
- CI smoke: at least 2 of 3 easy tasks resolved.
- Quality evals: `plan_quality`, `review_catch_rate`, `multi_turn_trajectory_quality`, `pr_description_quality`.
- Total cloud spend at or below $500.

## Architecture & Sub-Agents
Planner, Coder and Reviewer are `LlmAgent` nodes with Pydantic `output_schema`. Models come from `LiteLlm` via env vars, Gemini-first. The deterministic nodes are `fetch_issue`, `provision_sandbox`, `collect_diff`, `run_tests`, `human_gate`, `open_pr`, `report_failure` and `teardown`. A runner-wide `BudgetPlugin` enforces the caps. The deployment target is Agent Runtime, with Cloud Trace and the BigQuery Agent Analytics plugin.
