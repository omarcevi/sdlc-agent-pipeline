# AGENTS.md

Instructions for any coding agent (Claude Code, Gemini CLI, Codex, etc.) working in this repository.

## Project

A multi-agent system built on Google ADK 2.x that turns a GitHub issue into a tested pull request. A graph `Workflow` connects Planner, Coder and Reviewer LLM agents with deterministic function nodes. Code runs in hermetic sandboxes (local Docker or Agent Runtime Sandboxes). The system is measured with a hidden-test benchmark against a single-agent baseline.

- **Design spec (source of truth):** `docs/superpowers/specs/2026-09-29-sdlc-agent-pipeline-design.md`
- **Status:** Core loop and measurement harness implemented (local Docker sandbox): the multi-agent pipeline, the single-agent baseline, the matrix runner and the report. Task set: 20 tasks on three repos (15 dev, 5 sealed held-out). Latest comparison: `docs/results/2026-10-01-2b-comparison.md`. Live GitHub mode is built: the `app.live` CLI, the human approval gate and delivery as a pull request. A live run spends credits and writes to GitHub, so each one needs the owner's approval (hard rule 8). The replay site (`web/`) is built: a static viewer of seven curated Week 2B runs, converted and leak-checked by `bench/replay.py`. It is not live until the repository is on GitHub with Pages enabled. The Agent Runtime sandbox backend is not built yet.

Read the spec before making architectural changes. If the code and the spec disagree, stop and ask. Do not quietly pick one.

## Hard rules

1. **No AI attribution.** Never add Claude, Claude Code, or any AI tool as author, co-author or contributor. That means no `Co-Authored-By:` trailers, no "Generated with ..." lines in commits, PRs, docs, or a CONTRIBUTORS file. Commits use the repo owner's git identity only. This rule is about work in this repository. The pipeline's own pull requests, comments and commits on the demo repositories name the pipeline (`issue-to-pr`) and its model openly; that is the product's identity, not AI attribution of work in this repository.
2. **The sandbox gets no credentials and no network.** The GitHub token is read only by the orchestrator-side nodes `fetch_issue` (live graph), `open_pr` and `report_failure` (and, for live runs that end on a cap, an infra error, an agent error raised out of the graph or a crash, by the driver through `report_failure`'s `post_failure_comment`). It is read from the file named by `GITHUB_TOKEN_FILE`, never from the environment. Never pass it into prompts, session state, traces, logs or a sandbox.
3. **Tools go through `Environment`.** Agent tools must never call `subprocess`, `open()` or the host filesystem directly.
4. **Never trust model claims for routing.** Routing uses real `git diff` output and real test exit codes from function nodes.
5. **Benchmark integrity.**
   - Never tune prompts against `split: heldout` tasks, and never open or print their contents during development.
   - Never edit `hidden_tests/` to make a run pass.
   - Run `bench validate` after changing anything under `bench/repos/`.
   - The held-out run is dropped for now (owner, 2026-10-01; spec §19). Until the owner decides otherwise, the seal below still applies.
   - Held-out task directories (`bench/tasks/*-h[0-9][0-9]/`) are sealed: never open, print or diff them, not even as file names in a diff stat. Exclude them from review diffs with the pathspec `':(exclude,glob)bench/tasks/*-h[0-9][0-9]/**'`; a pattern without `/**` does not exclude the files inside.
   - Held-out tasks are never published, put in an eval dataset or probe, or audited.
   - Never convert or publish a run of a held-out task; `bench.replay` refuses one by its id. A replay is published only after `bench.replay check` passes and the owner has watched it.
   - Keep git output quiet around them: `git commit -q`, `git cherry-pick ... >/dev/null`, `git merge --no-stat`. Run pytest with `--tb=no` when held-out tasks are collected. Never review a held-out change in a GitHub PR's file view.
6. **Keep the cost guards.** The budget plugin, sandbox TTLs and loop bounds stay on. Changing their defaults needs the owner's approval.
7. **Don't change model names unless asked.** Models are configured through env vars (`PLANNER_MODEL`, `CODER_MODEL`, `REVIEWER_MODEL`). Bench runs take their models from `--preset`; the three role variables configure `app/agent.py`.
8. **Never deploy, create cloud resources, or push to GitHub without explicit approval** from the owner, given in the current session.

## Runtime wiring

- `app/pipeline.py` builds the graph; `app/agent.py` exposes it to agents-cli as `root_agent` / `app` (the bench graph only; a test pins that it has no `human_gate` or `open_pr`); `app/driver.py` (`run_pipeline`) is the entry point for bench and live runs and the only place that releases the sandbox of a run it drives. `app/live.py` is the only builder of the live graph.
- Live graph and human approval: `build_workflow(models)` is the bench graph (ends at `deliver_patch`, never pauses; its edges and the baseline's are pinned by tests). `build_workflow(models, live=True)` uses `fetch_live_issue` as `fetch_issue` and adds `deliver_patch → human_gate → route_approval → {approved: open_pr, rejected: report_failure}`. `human_gate` (`app/nodes/gate.py`, `rerun_on_resume=False`) yields `waiting for human approval`, then ADK's `RequestInput` (`interrupt_id` `approve-<run-id>`, payload `app.approval.ApprovalRequest`: branch and title from the same `pr_text` calls `open_pr` uses, the issue URL, and the body from `app/nodes/finish.py::published_body`, the one helper that renders the body for `deliver_patch`'s `pr_body.md`, the gate and `open_pr` (the gate's has no approver footer); files and counts; patch path and hash; test result; review verdict; cost and tool calls), and the run's first pass ends with a pending `adk_request_input` call. The driver then releases the sandbox, asks `run_pipeline(..., approver=...)` (an `Approver`: `ApprovalRequest` → `ApprovalDecision(approved, approver, patch_sha256, note)`; `approved` is a strict boolean, so a malformed decision fails closed) under `APPROVAL_TIMEOUT_S`, and resumes the same session (session state carries `patch_sha256`, `patch_created_at`, `protected_paths`) with one function response holding the decision, under a 300 s cap of its own (expiry: `infra`, "resumed run exceeded 300 s wall clock", plus "; the pull request may have been opened" after an approval, since `open_pr` may stall after GitHub created it; that case gets no failure comment, because the pull request, if it exists, is the reply); the resumed events are appended to the same `events.jsonl`. No approver: `failed` / `infra`, "approval needed but no approver", at once. A timeout is the decision `approved=False`, empty approver, note "approval timed out" (no login, so the failure comment mentions no one). A `KeyboardInterrupt` or cancellation while waiting for the approver is the same kind of decision with note "approval cancelled": the run is resumed as for any rejection (one comment by `report_failure`) and its record written; a cancellation of the whole run (a cancel request on the run's task) is then raised again, while one from inside the ask (Ctrl-C at the CLI's prompt) is not. A cancellation at any other point (the first pass, the gate, the resumed pass, the sandbox release) still leaves a record: `failed` / `infra`, "run cancelled" (plus "; the pull request may have been opened" after an approval), written after the sandbox is released, with no comment; the cancellation is then raised again. The root span gets the record's outcome first, and a crash during the resume surfaces as the crash even when the run was also cancelled. `route_approval` routes `approved` only when `approved` is true and the decision's hash equals state `patch_sha256`, and passes the decision on as its output (which `open_pr` reads); otherwise state `failure` (kind `rejected`: "not approved by <login>[: <note>]", "approval was for a different patch", or the note) and `approver` (read by `report_failure` for its "Decision by" line). `TerminalApprover(login)` shows repository, issue, base and planned branch, test result and verdict, diff stat, the patch (first 400 lines, then its path), title and body, then cost and tool calls. Each shown line is cut at 500 characters and the file list at 100 entries; Cc/Cf, Zl/Zp and the default-ignorable characters are shown as escapes; on a terminal, type-ahead is discarded before the prompt (termios `TCIFLUSH`). Only the exact word `approve` approves, and the decision carries the hash of the patch file it showed. A `GitHubError` or `GitHubConfigError` from `open_pr` (401, 403, 422, a branch at another commit) ends the run `failed` / `infra`, "GitHub refused the pull request", and a `GitHubUnavailable` (5xx, 429, rate limit, transport, after the retries) "GitHub was unavailable while opening the pull request": `record.json` holds no GitHub response text. `events.jsonl` may keep ADK's error event for the failed node, with the client's error text (method, path, status and GitHub's message, scrubbed of the token, the message capped at 200 characters); it is a local debug log, and that is accepted. `open_pr`'s own `RuntimeError` guards (not approved, hash differs, unsafe or protected path, `.git` path, patch does not apply, symlink, old git) and an `ArchiveError` there stay crashes: earlier nodes enforce each of them, so reaching one is a harness bug, and the crashed run keeps its record. `RunRecord` gains `pr_url`, `comment_posted` (from the outcome) and `approval_wait_s`; `duration_s` excludes the wait.
- `app/baseline.py` builds the single-agent baseline graph (`build_baseline_workflow`): fetch, provision, one `solo` agent (same tools, sandbox, guardrails and budget as the coder), `route_solo`, diff, tests, deliver, with the same 3-return test-fix loop. It drops only the planner and the reviewer. Both systems run under the same per-run caps (cost, tool calls, wall clock).
- Runner-wide plugins, in order: `BudgetPlugin` (cost and tool-call caps), ADK's `ReflectAndRetryModelPlugin(max_retries=2)` (retries malformed function calls), `GuardrailPlugin` (shell and protected-path checks), `SandboxReleasePlugin` (`app/agent.py` only: at the end of a run, or on its error, it releases the sandbox that run started, because a run under agents-cli has no driver `finally`; the driver does not install it), then the BigQuery analytics plugin when it is enabled. The driver inserts an internal tracker, used for failure classification, right after the budget plugin. The order matters: a plugin that returns a value stops the ones after it.
- The driver bounds the whole event loop with `RUN_TIMEOUT_S` (`asyncio.timeout`); it cancels the in-flight work cooperatively (not a hard kill: a task that swallows cancellation could still block); only the cap's own expiry becomes a `budget` failure, an outer cancellation still propagates (after the run's "run cancelled" record is written). `bench.matrix` waits `INFRA_RETRY_PAUSE_S * k` (30 s default) before infra rerun k.
- Each non-streaming Gemini call is bounded by `MODEL_CALL_TIMEOUT_S` in `ResponseToolGemini.generate_content_async` (`app/models.py`, an `asyncio.timeout` around the whole call, the SDK's retries included): a silent call is cancelled and sent again once, and a second silence raises `ModelCallStalled`, which the driver records as an `infra` failure ("model call stalled twice ..."), so the matrix reruns it. Every timeout counts toward the run's `model_stalls` (`RunRecord`, `record.json`; a per-run counter in the `RUN_STALLS` context variable), and a result row adds them up over its infra reruns, like cost; `bench.report` lists stalled-twice runs per configuration in their own section. google-genai's own `HttpOptions.timeout` is not used: on the aiohttp transport it raises a bare `TimeoutError` that the SDK does not retry. LiteLLM models and streaming calls are not bounded.
- Task format (`app/task_store.py`): `task.yaml` also takes `tempting: bool` (default false) and `levers: [...]` (from `LEVERS`: `multi_file`, `distant_symptom`, `doc_rule`, `regression_risk`, `shortcut`). A tempting task ships a `shortcut/` overlay (applied after `plant/`, never together with `solution/`) that must pass the visible tests and fail the hidden ones; `bench.validate` checks this and prints only fixed problem strings. Result rows and the report also carry repo and difficulty breakdowns.
- Delivery (`app/nodes/finish.py`, public text in `app/pr_text.py`): `deliver_patch` writes `patch.diff`, `pr_body.md` (the rendered pull request body) and state `patch_sha256` (SHA-256 of the full diff, UTF-8) and `patch_created_at` (the fixed commit date, so a re-run makes the same commit) in both modes. The source archive is extracted by the same `app/archive.py` as live intake (refused if it holds any `.git` path, a link, a case-folded duplicate name, or too many bytes or files), and host git runs with `safe.bareRepository=explicit` so an archive that looks like a repository is never discovered (delivery needs git 2.38 or newer). In live mode `open_pr` checks the diff hash against the state and the approval, refuses `.github/` and protected paths, applies the patch with host `git apply` to the pinned source archive, and publishes through the Git Data API (blobs, tree on the pinned base tree, commit by `issue-to-pr pipeline`, branch `issue-to-pr/<n>-<run-id>`, pull request); there is no clone and no push. `report_failure` in live mode also posts one marked comment on the issue through `post_failure_comment`; a comment that fails is logged and recorded as `comment_posted: false`, never as a different outcome. A live run whose outcome the driver produced after its issue was fetched (an exception the driver classified, of any kind: a cap, an infra error, an agent error raised out of the graph such as a model 400 or malformed output; a crash; or no outcome at all) never reached `report_failure`, so the driver posts that comment (decision 10A) through the same `post_failure_comment`, after writing `record.json` (rewritten with `comment_posted: true` when it is on the issue) and under a 120 s cap. The comment says what happened and nothing more (`_public_reason`): a budget reason as it is (built from numbers only); an infra reason only when it is one of the driver's own fixed strings (`PUBLIC_INFRA_REASONS`: no approver, no outcome, GitHub refused or unavailable at delivery, the resume cap), otherwise "an infrastructure error (sandbox, model service or GitHub) stopped the run; the details are in the run's local record"; an agent failure "the agents could not produce a usable answer; …"; a crash "the pipeline stopped on an internal error; …". So exception text, sandbox and provider errors (home paths, cloud project ids) stay in `record.json`. A failure to post is logged and changes neither the outcome nor a crash, which is still raised. The driver never comments when the graph's `report_failure` produced the outcome (declined, agent-failed in the graph, rejected), on a refused or cancelled run, or after an approval when the resume cap expired. Public text: model-written text appears only inside code fences the text cannot close, real data is rendered from fields, the body refers to the issue once and uses no closing keyword, and every pull request body and failure comment ends with a footer naming the pipeline, the run and the models. `budget` state lists the models seen in the run (`models`).
- Scoring (`bench/score.py`) runs inside a sandbox; model-written code never runs on the host.
- Replay site. `web/replays.yaml` (note, caps; per run `run_id`, `caption`, optional `pair`, `caps`, `allow`) lists curated dev bench runs. `bench.replay build` checks each entry (the run-id shape of every entry before any file is opened, `bench.probes.dev_task`, the run files and record, exactly one scored dev results row with held-out rows skipped by `task_id`, pair, caption), converts it with `convert_run`, refuses replays over 1 MB (warns over 300 KB), leak-checks the finished set in a temporary directory, then swaps it into `web/public/replays/` as a whole. It never calls `list_tasks()`. `convert_run` builds a replay from `events.jsonl`, `record.json` and the results row from an allowlist of fields, rewrites host paths, sandbox and container names, the project id, `REPLAY_REDACT` values and run paths, cuts long strings, and refuses on a leak-check hit; `bench.progress.call_detail` is shared by progress lines and replay labels. `bench/replay_check.py` (standard library only) is the leak check; it exempts a string that is exactly a bench run id from `high-entropy` only. `bench.replay` exits 2 before importing `app` when `BQ_ANALYTICS_ENABLED=1`, because importing `app` runs `app.agent`'s analytics setup.
- `.github/workflows/pages.yaml` ("Replay site") runs on pull requests and pushes to `main` that touch `web/**`, `bench/replay_check.py` or the workflow, and on `workflow_dispatch`. The build job runs the leak check with bare `python3` (`REPLAY_REDACT` from the repository secret), then `npm ci`, typecheck, tests, build and the Playwright smoke test in `web/`, and uploads `web/dist` as the Pages artifact except on pull requests. Permissions are `contents: read` at the top; only the `deploy` job has `pages: write` and `id-token: write`, and it deploys only on `main` once Pages is set to "GitHub Actions". Every action is pinned to a full commit SHA with its tag in a comment; to re-pin, query `refs/tags/<tag>` and `refs/tags/<tag>^{}` with `git ls-remote` and use the peeled commit.
- Reviewer probes measure the reviewer on prepared patches. A probe is `bench/review_probes/<probe-id>/` (`REVIEW_PROBES_DIR`) holding `probe.yaml` (`task_id`, `kind: bad | good`, `source: shortcut | bench-run | hand-written`, `source_run`, `note`) and `patch.diff` (a `git diff` against base + plant, the form the pipeline produces). Probe ids are opaque (`rp-NN`); the kind lives only in `probe.yaml`, which only `app.review_probe.load_probe` (for the task id) and the harness read. The probe set (12 probes, 6 bad and 6 good, over 8 dev tasks) was chosen by a fixed rule from the Week 2B single-agent runs; `bench/review_probes/SELECTION.md` records the selection and the reading rule for probe results. `app/review_probe.py` builds the probe graph (workflow name `issue_to_pr`, input `ProbeRequest`): load probe, provision, planner, route, apply the patch in the sandbox, the pipeline's own diff and test nodes, reviewer, record verdict (a failing visible test is `probe_invalid`, an infra failure). The coder never runs. `bench/probes.py` stores and validates probes against the visible and hidden tests (dev tasks only; a held-out task id is refused before anything of it is read) and `bench/review_probe.py` runs them through `bench.matrix` (`RunSpec.variant` is the probe id; rows add `probe_id`, `kind`, `verdict`, `must_fix`) and reports the catch rate and the false-alarm rate. A bad probe passes the visible tests and fails the hidden ones; a good probe passes both. No probe changes after a reviewer result is seen.
- Live intake (`app.nodes.intake.fetch_live_issue`, live graph only): `RunRequest` takes `mode="live"`, `repo`, `issue_number`, `base_ref`. Preconditions in order (repository in `LIVE_REPOS`, token loads, issue exists, is not a pull request, is open, author allowed, `agent-ok` last added by an allowed login, no open pipeline pull request), then the base branch is pinned to a commit and its tarball saved to `runs/<run-id>/source.tar.gz` (extracted on the host by `app/archive.py`: gzip or plain tar only, the checksum verified, the decompressed size bounded while reading, at most 5000 files and 50 MB, no links or special files, any `.git` path component refused, case-folded duplicate names refused). A failed precondition raises `RunRefused`; the driver records outcome `refused` (failure kind `none`, cost 0, nothing written to the remote, no comment). The bench graph's `fetch_issue` refuses a live request without reading the token. `RunRecord` gains `mode`, `base_ref`, `base_sha`, `base_tree_sha`; `Outcome` gains `pr_opened`, `rejected`, `refused`.
- Live CLI (`app/live.py`):
  - Refusals (exit 2, one `error:` line, nothing run): stdin is not a terminal; `--approver` not in `LIVE_ALLOWED_USERS`; `--repo` not in `LIVE_REPOS`; a bad run id (1 to 64 of letters, digits, `.`, `_`, `-`, starting with a letter or digit); a bad timeout setting; the issue's lock is held; `runs/<run-id>` already exists (the CLI creates it exclusively, so a reused id never overwrites an earlier run's record or reuses its comment marker and branch). It loads `.env` first.
  - Default run id: `live-<UTC stamp>-<name>-<n>`, the repository name cut to 32 characters; the stamp comes first so the branch name, which keeps 40 characters of the run id, tells two runs on one issue apart.
  - Lock (`app/live_lock.py`, standard library only): `runs/.locks/<owner>__<name>__<n>.lock`, lowercased, created with `O_CREAT | O_EXCL`, holding the PID, with an exclusive `flock` kept while the run lasts, removed at exit. A file whose `flock` is free and whose PID is not alive is stale and is replaced; only the holder of the `flock` of the file currently at the path may remove it, so two processes cannot both replace one stale lock. A file with no PID counts as held.
  - Run: enables tracing like `bench.run`, builds `build_workflow(RoleModels.from_env(), live=True)` and runs `run_pipeline(RunRequest(mode="live", ...), approver=TerminalApprover(login))` with live progress unless `--quiet`, then prints outcome, reason, pull request URL, cost and run directory (escaped). The CLI never reads the token.
  - Ctrl-C, through a loop SIGINT handler: at the prompt it cancels only the prompt, so the driver records a rejection ("approval cancelled"); while the decision is delivered (after the prompt was answered, timed out or interrupted) the first press prints "delivering the decision; press Ctrl-C again to abort" and the second stops the run; at any other time a press stops the run; one more press after that raises `KeyboardInterrupt`. A stopped run still has its record ("run cancelled"), which the CLI prints.
  - Exit codes: 0 when the run finished, whatever its outcome; 1 when it crashed; 130 when Ctrl-C stopped it; 2 for the refusals above. The record is written in the first three cases.
  - The answer is read by a daemon thread through a queue that the CLI releases when the run ends (and again in its own `finally`), so an approval that timed out never keeps the process waiting for the terminal.
- Issue text reaches every agent only as the `{issue_text}` block `<issue>\nTitle: ...\n\n...\n</issue>` (`format_issue_text`, which neutralises the opening fragment of any `<issue` or `</issue` in the assembled text, in raw, entity, Unicode-lookalike and invisible-character forms, and caps its length), in the instruction of the planner, coder, reviewer and solo agent. `provision_sandbox` outputs the fixed message `Plan the change for the issue in your instructions.`, so no agent's request holds the raw issue elsewhere, or the run id (a test pins this for the bench, baseline and probe graphs). Benchmark numbers from before this prompt change (Weeks 2A and 2B) are a different prompt version: do not pool them with later ones. Rows record it (`prompt_version`, constant in `app/prompts.py`) and `bench.report` enforces it; bump the constant with any change to an agent's instruction. `bench.review_probe` enables and flushes Cloud Trace like `bench.run`. `issue_text_differs` in `bench.score_run` ignores CRLF versus LF and trailing whitespace.
- Tracing (`app/tracing.py`) is opt-in. With `TRACE_TO_CLOUD=1`, `bench.run` exports to Cloud Trace: the driver's root span `issue_to_pr.run` (task, run ID, outcome, cost, tool calls) with ADK's workflow, agent, model-call and tool-call spans under it.
- The pipeline's git directory is `/workspace/.pipeline-git`, outside the worktree. Diffs are taken against the baseline commit recorded in state as `baseline_sha`.
- Gemini agents return structured output through ADK's `set_model_response` tool (`app/models.py` reports `output_schema_and_tools=False`), because native output schema + tools loops on the tool call on gemini-3.8-flash. That tool call counts toward the per-run tool-call cap.

## Workflow

This project follows the `agents-cli` lifecycle: scaffold → build → evaluate → deploy → observe.

- Requires `agents-cli` ≥ 1.7.0. Upgrade with `uv tool upgrade google-agents-cli`, then run `agents-cli update`.
- Use `uv` for everything Python (`uv sync`, `uv run ...`). Never call `pip` directly.
- The replay site in `web/` uses Node 24 (`web/.nvmrc`) and npm; `web/package-lock.json` is committed and changes only together with a dependency change.
- Before writing agent code, study the reference recipes listed in spec §17 (`google/adk-samples` → `core/python/...`).
- Run `agents-cli infra single-project` **before** the first `agents-cli deploy`.

## Testing conventions

- **pytest checks code correctness:** graph routing (using the scripted fake `BaseLlm`), guardrails, budget math, schemas, and the environment backends. pytest must never assert on real LLM output content.
- **Agent behaviour** is measured by `agents-cli eval run` (quality metrics) and the `bench/` benchmark (the resolve rate).
- Write a failing test before implementing deterministic code.
