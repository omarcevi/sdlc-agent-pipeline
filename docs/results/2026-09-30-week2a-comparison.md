## What happened

Everything above this line is generated by `bench.report`. This section is written by hand from the run records, the event logs and the patches. The run log next to this file records each step, its cost and what went wrong.

### The short version

On five small tasks (three easy, two medium) with Gemini 3.8 Flash, the single agent resolved 15 of 15 runs and the multi-agent pipeline 12 of 15. The three multi-agent failures are all the same task and the same cause: a tool-call cap that applies to the multi-agent coder and not to the single agent. This run does not show that one design solves more issues than the other. It shows that these tasks are too easy to separate them, and that the caps are not yet equal for both systems.

### The three failures

All three are `tc-001` (an easy bug: `add --due` rejects ISO datetimes with a timezone), one in each repeat, and all end with `coder exceeded 25 tool calls in one turn`.

- In each run the coder had already edited `taskcli/dates.py`, written a new test file and run the tests. The 26th call was a last `git diff`, `git status` or `pytest`.
- Before its first edit the coder made 20 to 22 calls. Of those, 13 to 17 were shell commands, and 11 to 15 of them tried inputs on `datetime.fromisoformat`, mostly one input per call.
- A run that ends on a cap saves no patch, so these three cannot be scored after the fact. They are "did not finish within the cap", not "could not solve it".
- The single agent has the same habit. It used 31, 38 and 30 tool calls on `tc-001` and resolved it each time. Every one of those is above 25, so the coder's cap would have stopped it too.

If the three per-turn-cap failures are set aside, both systems resolved 12 of 12 on the other four tasks.

### What the planner and the reviewer added

Nothing that this task set can measure.

- The reviewer approved every patch it saw (9 of 9) on the first round. No run went back to the coder after review, and no run went back after failing tests.
- The two systems wrote near-identical fixes. For `tc-002` all six patches change the same line to the same expression.
- On the four tasks that are not the trap, the planner made 6 to 10 tool calls per run and the reviewer 4 to 8, counting the call that returns the structured answer.

### Cost and time

| | multi (flash) | single (flash) |
|---|---|---|
| Total | $2.01 | $2.27 |
| Four tasks both systems finished, 12 runs each | $1.42 | $1.54 |
| Trap task, per run | $0.004 to $0.005, 11 to 17 s | $0.008 to $0.010, 19 to 45 s |
| Tool calls per run on `tc-002` to `tc-004` | 22 to 35 | 14 to 25 |

The costs are close. The multi-agent pipeline makes more tool calls, because three agents each read the repository, but each agent starts with a short context. The single agent makes fewer calls and carries one long, growing context. On this run those two effects roughly cancel. The planner declines the trap issue at about half the single agent's cost: it looks at less of the repository before answering (3 tool calls against 5 or 6).

### Patches

Every resolved patch was read by hand, not only flagged ones: 9 multi-agent and 12 single-agent. Each changes one or two files under `taskcli/` and adds one new test file. None touches pytest configuration or internals, an existing test file, or `.github/`. The audit raised no flags.

### Pro: did not complete

The plan included one repeat of each system on `gemini-3.1-pro-preview`. It did not produce results.

- With three runs at once, Vertex returned `429 RESOURCE_EXHAUSTED`. Three tasks used all three attempts within a minute, because a rerun after an infra failure started immediately.
- In the two multi-agent runs that got as far as the reviewer (`tc-004` in the first attempt, `tc-001` in a one-at-a-time rerun), the reviewer's model call never returned: 23 and 21 minutes with the connection open. Both runs were stopped by hand. The planner and the coder had worked on Pro, and the tests had passed in both.
- The single agent on Pro was not run, because it would have had nothing to be compared with.
- The cause of the hang is not known. It was the same stage both times, so it is probably not a network accident. Finding out needs a small diagnostic run.

What this exposed is a gap in the harness: nothing limited how long a run could take. The caps counted dollars and tool calls, not minutes. A wall-clock cap per run and a pause before rerunning an infra failure were added after this run. The partial Pro rows are kept in `results/aborted/` and are not in the tables above.

### What this run does not show

- **It is not a benchmark yet.** One demo repository, five tasks (three easy, two medium), all in the dev split, with prompts that were written while looking at these tasks. Three repeats show run-to-run variation on the same five tasks; they do not make the sample bigger.
- **The caps are not equal.** The 25-calls-per-turn cap applies to the multi-agent coder only, and the 75-calls-per-run cap is shared by three agents there. This is the whole of the measured gap.
- **Declining is not symmetric.** The planner decides once whether to decline. The single agent can decline on any of its turns. On this run both declined the trap issue every time.
- **The multi-agent pipeline gets more coder turns** (up to six, against four). No run used a second turn, so it made no difference here.
- **Scoring has a known limit.** Hidden tests run in a fresh sandbox, but a patch whose own code interferes with pytest while the hidden tests run could still pass. Reading every patch is the check for that.
- **Cost is an estimate** from token counts at list prices. Cached tokens are billed at the full rate, so it overstates.

### What comes next

- Make the tool-call caps equal for both systems, or justify the difference, then rerun Flash (about $5). This is the owner's decision, because the caps are cost guards.
- Find out why the reviewer's call on Pro does not return, then run the Pro comparison.
- The coder's one-call-at-a-time probing is a prompt-tuning target, but only once there are enough tasks to measure a change (Plan 2B: more repositories, harder tasks, a held-out split).
