# Multi-agent vs single-agent under equal caps

Caveat: every configuration ran the same 5 tasks with 3 repeats each. Within a repeat, one task is 20 points of resolve rate (100 / 5). Repeats rerun the same tasks, so they show run-to-run variation and do not make the sample of tasks bigger.

The resolve rate's denominator (the counted column) holds only runs that are neither infra failures nor crashed; those runs are shown in their own columns. Crashed runs are not also counted under infra. Every run is in exactly one of resolved, unresolved, agent, budget, infra or crashed, and those six columns sum to runs. Unresolved is a counted run that was not resolved and has no failure kind: a wrong patch, a wrong decline, or a trap that was patched.

## What happened

Everything above this line is generated by `bench.report`. This section is written by hand from the run records, the event logs and the patches.

### Why this rerun exists

The first comparison, earlier the same day, ended 12 of 15 for the multi-agent pipeline and 15 of 15 for the single agent ([report](2026-09-30-week2a-comparison.md)). All three failures were one task stopped by a cap of 25 tool calls per coder turn, which did not apply to the single agent. The owner then removed that cap, so both systems run under the same limits per issue: $1.00, 75 tool calls and 25 minutes. This is the same benchmark run again under those limits. Nothing else changed: same tasks, same prompts, same model.

### The result

Both systems resolved 15 of 15. The earlier gap was the cap.

- `tc-001`, the task that failed three times before, was resolved in all three multi-agent repeats, with 38, 44 and 45 tool calls in the run.
- No run hit any cap. No run failed its tests, and the reviewer approved all 12 patches it saw on the first round, so neither loop was entered.
- No infra failures, no reruns, no crashed rows, no audit flags.

### What the extra agents cost

On these tasks the planner and the reviewer did not change any outcome, and they were not free.

| | multi (flash) | single (flash) |
|---|---|---|
| Resolved | 15 of 15 | 15 of 15 |
| Total cost | $2.42 | $2.15 |
| Median time, the four real tasks | 291 s | 160 s |
| Tool calls per run, the four real tasks | 26 to 45 (mean 34) | 16 to 29 (mean 22) |
| Trap task | $0.004, 12 to 16 s | $0.010 to $0.014, 26 to 30 s |

The multi-agent pipeline cost about 13% more and took about 1.8 times as long on the tasks that need a patch. It was cheaper and faster only on the trap issue, where the planner declines after a short look.

This is a statement about five small tasks, not about the design. A planner and a reviewer can only earn their cost on tasks where a plan prevents a wrong turn or a review catches a wrong patch, and none of these tasks is like that: every first patch was correct.

### Patches

All 24 patches were read (12 per system). Each changes one or two files under `taskcli/` and adds one new test file. None edits an existing test file, pytest configuration or `.github/`. The two systems again wrote near-identical fixes.

### What this run does not show

- **It is still not a benchmark.** Five small tasks (three easy, two medium) on one repository, all in the dev split. Both systems are at the ceiling, so the run cannot rank them.
- **Run-to-run variation is large.** The single agent used 18 to 26 tool calls on `tc-001` here and 30 to 38 in the first run, with nothing changed on its side.
- **Declining and coder turns are still not symmetric** between the systems (see the first report). Neither mattered here.
- **Cost is an estimate** from token counts at list prices.
- **No Pro results.** The reviewer's model call on Gemini 3.1 Pro did not return in the first run, and that is not yet explained.

### What comes next

A task set that leaves headroom: two more repositories, harder tasks (fixes that span modules, symptoms far from the cause, shortcuts that pass the visible tests only), and a held-out split written by a separate author and run once at the end.
